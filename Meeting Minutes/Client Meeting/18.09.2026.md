## Meeting Purpose

## Discussion

### Topic 1: Data Collection Status and Difficult Company Sources

The team reported that collection is working for the currently accessible company sources and that the collected job data is being compiled into a weekly or biweekly dataset.

NVIDIA and Waymo remain difficult sources because their proprietary career portals are highly Application Programming Interface (API)-driven and return JavaScript Object Notation (JSON) data through internal requests. Previous browser-based attempts produced incomplete or inconsistent results rather than a reliable full set of job advertisements.

LinkedIn was identified as a possible alternative source for these companies. RapidAPI was mentioned as one possible service for retrieving LinkedIn-related job data, but its cost, completeness and consistency have not yet been confirmed.

The client agreed that the team should investigate the LinkedIn/API route. However, the project should not be blocked if a reliable extraction method cannot be found for these companies.

### Topic 2: Chinese-Language Data and Translation

A substantial portion of the Chinese-company job data is written in Chinese. The team has used Microsoft student translation credits for manual experiments, but this is not sustainable for a recurring collection pipeline.

Open-source and hosted models, including Qwen and models available through OpenRouter, were discussed as possible translation options. The following constraints were identified:

- Local Large Language Models (LLMs) place a heavy computational load on student laptops.
- Free hosted models may be unavailable or may produce inconsistent results.
- Paid models introduce an operating cost, although some models available through OpenRouter are inexpensive.
- The selected model and provider must comply with current UWA requirements.

No final translation service was selected. A smaller or low-cost hosted model will be tested before the team commits to an implementation.

### Topic 3: Classification and Skill-Extraction Approaches

The team presented three possible approaches.

#### Approach 1: No LLM

- Maintain a team-defined skill vocabulary and matching rules.
- Clean and tokenise the job descriptions.
- Convert the extracted information into embeddings.
- Use the existing local clustering algorithm to group similar jobs.
- Manually interpret and label the resulting clusters.

The current prototype produces approximately 40 clusters and distinguishes broad cluster leanings such as technical, corporate and mixed roles. It also reports common skills and example job titles.

This approach is fast, inexpensive, reproducible and easy to run. Its main limitation is that it can only identify skills included in the maintained vocabulary, and the clustering algorithm cannot independently reason about suitable cluster names.

#### Approach 2: Hybrid LLM and Local Clustering

- Use an LLM to extract tools, domain skills, qualifications, seniority and supporting evidence from each job advertisement.
- Retain the existing local clustering algorithm to group jobs using the extracted skills.
- Manually review and label the final clusters where required.

This approach can produce richer job-level information while keeping the clustering process relatively deterministic. However, the team must validate model consistency, cost and processing time.

A local open-source LLM experiment processed only 14 job advertisements in approximately 40 minutes and placed a heavy load on the computer. This was considered technically possible but unsuitable for routine execution on student laptops.

#### Approach 3: LLM-Led Extraction and Clustering

- Use a hosted LLM to process every job advertisement.
- Use a second LLM pass to create or label clusters.

The current dataset contains approximately 3,500 raw job advertisements. Initial filtering reduces this to approximately 2,500–2,600 records after duplicates and unsuitable records are removed. A second LLM pass for clustering would increase processing cost and may still produce inconsistent labels across independent requests.

The client preferred the team's existing local approach as the baseline because it is fast, inexpensive, clean and deployable. An LLM may remain an optional enhancement for richer skill extraction or translation after testing.

### Topic 4: Cluster Labels and Generic Job Titles

The team explained that a conventional clustering algorithm can identify similar jobs but cannot reliably explain what each cluster represents or generate consistent generic job titles.

The client confirmed that skills and skill clusters are more important than producing a perfect job-title taxonomy. Manual assignment of generic job titles was considered practical because the expected number of broad job categories is manageable.

The client offered to review the final cluster list and propose generic titles for the categories.

### Topic 5: Required Data Granularity

The system should preserve both job-level and cluster-level results.

**Job-level results should include, where available:**

- Extracted tools and technologies.
- Domain skills.
- Qualifications.
- Seniority and experience requirements.
- Supporting evidence from the original job advertisement.
- The cluster assigned to the job.

**Cluster-level results should include:**

- Cluster identifier and generic label.
- Number of jobs in the cluster.
- Common skills.
- Example job titles.
- Broad role type, such as technical, corporate or mixed.

Job-level information must be retained because less-common tools may disappear from an aggregated cluster summary. The intended processing flow is:

1. Collect job advertisements.
2. Extract job-specific skills and related information.
3. Cluster jobs using the extracted skills.
4. Assign clear generic labels to the clusters where required.
5. Provide both detailed job data and aggregated cluster data to the dashboard.

### Topic 6: Dashboard Audience and Required Analytics

The client explained that his own detailed analysis can be supported through a spreadsheet export. The dashboard should instead target a broader audience, particularly students and other users planning careers in autonomous vehicles.

Three priority analytics were identified:

1. **Total job numbers over time** – show whether the market is growing or declining and make seasonal changes visible.
2. **Skill-demand trends over time** – show how demand for technologies and skills changes, such as movement from one programming language to another.
3. **Geographic distribution of jobs** – show where relevant autonomous vehicle jobs are located.

Weekly collection was discussed as the basis for trend analysis.

Location reporting will initially use country-level data because city and suburb names are inconsistent, particularly in the United States. Multi-country or multi-region job advertisements will require additional cleaning.

The client preferred three focused dashboard views over a broad, generic business-intelligence dashboard. The final frontend technology remains a team decision.

### Topic 7: Deployment and Operating Model

The client confirmed that the classification pipeline does not have to be permanently deployed as a hosted service.

An easy-to-run local script is acceptable. If the setup becomes complex, the pipeline can be packaged in a container so that it can be run consistently.

If the team chooses a local-LLM approach, the client advised that a UWA NVIDIA DGX Spark system with substantial unified memory may be available. It could run the processing pipeline as a scheduled weekly job.

The DGX/local-LLM option was treated as an available but higher-effort path. The full team must review the workload and delivery risk before committing to it.

The data and classification pipeline may have a usable result within approximately one week. However, the complete website/dashboard timeline was not confirmed because the full team was not present.

The team agreed in principle to arrange a demonstration after the dashboard reaches a usable stage and will provide a realistic date following an internal team discussion.

## Key Decisions and Agreed Direction

### Decision 1: Difficult Sources Will Not Block the Project

The team will investigate LinkedIn or another API-based route for NVIDIA and Waymo. If no reliable source is available, these companies will not be treated as blocking dependencies.

### Decision 2: Local Skill Extraction and Clustering Is the Preferred Baseline

The client preferred the team's existing lightweight local pipeline because it is fast, inexpensive and easy to deploy. The full team still needs to confirm the final implementation.

### Decision 3: LLM Use Is Optional

An LLM may be used for translation or richer job-level skill extraction if testing shows that it is consistent, affordable and compliant with University requirements. LLM-based clustering is not required for the baseline solution.

### Decision 4: Skills Are the Main Analytical Focus

The project will prioritise extracting job-specific skills and producing skill-based clusters. Both job-level details and cluster-level summaries will be retained.

### Decision 5: Cluster Labels May Be Assigned Manually

Manual review may be used to assign understandable generic titles to clusters. The client is willing to assist after receiving the cluster list.

### Decision 6: The Dashboard Will Focus on Three Views

The dashboard will focus on:

- Job-count trends over time.
- Skill-demand trends over time.
- Job locations.

### Decision 7: Location Will Initially Be Country-Based

Country-level reporting will be used for the first implementation. Multi-region records will be reviewed and cleaned separately.

### Decision 8: A Local Script or Container Is an Acceptable Delivery Method

The classification pipeline may be delivered as an easy-to-run local script or container. Permanent hosted deployment is not required. Use of UWA DGX infrastructure remains optional.

### Decision 9: External User Feedback Will Be Collected

The team will arrange a demonstration for a robotics research or PhD student group after a usable dashboard is available. The date remains to be confirmed.
